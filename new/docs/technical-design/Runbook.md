# Runbook

This document provides operational instructions for managing, monitoring, and troubleshooting the Hospital Management System Backend.

## 1. Tenant Provisioning Failures
Tenant isolation is managed via Postgres schemas. When a new tenant is created via `POST /tenants`, the `AccountsService.provisionTenantSchema()` function dynamically provisions their tables by iterating through standard migrations.

### Symptoms
- 500 Internal Server Errors when a specific tenant tries to log in or use the API.
- Logs indicating: `relation "orders" does not exist` or `schema "tenant_<id>" does not exist`.

### Resolution
1. Verify if the tenant schema was actually created in the DB:
   ```sql
   SELECT schema_name FROM information_schema.schemata WHERE schema_name = 'tenant_XYZ';
   ```
2. If it's missing or incomplete, the provisioning process failed midway. Check the API logs for TypeORM query runner failures during the migration. You may need to manually replay the migrations against that schema or drop the tenant and recreate it.

## 2. Event Archiver and Audit Logs Missing
We use asynchronous TypeORM `EntitySubscriberInterface` hooks to capture Audit Logs and Reporting Events without blocking the core business transaction.

### Symptoms
- Actions occur, but no records appear in `audit_records` or `reporting_events`.
- In test environments: "Jest did not exit one second after the test run has completed."

### Resolution
1. **Check Logs for Publisher Errors**: 
   Since the publishers wrap writes in a fire-and-forget `try/catch` block, they will never crash the request. You must inspect the application logs for `[PersistingAuditEventPublisher]` or `[PersistingReportingEventPublisher]` errors.
2. **Schema Mismatches**: 
   A common issue is attempting to publish an event after the TypeORM connection releases the `tenant_<id>` search path. The logs will say `relation "reporting_events" does not exist`. Ensure any deferred processing inside `afterTransactionCommit` utilizes a new `queryRunner` initialized with the proper schema.

## 3. Dealing with Test Flakiness (inTenant utility)
The `inTenant()` testing utility executes the entire test suite inside a single rolled-back transaction to preserve database state.

### Symptoms
- "Transaction already released" errors in Jest.
- Lifecycle hooks (`afterTransactionCommit`) never firing during standard `expect()` blocks.

### Resolution
- Remember that `afterTransactionCommit` will **only** fire at the very end of the `inTenant` block, not between sequential actions inside the block. If your test asserts on data generated by an `afterTransactionCommit` hook, it will fail because the test checks *before* the hook has run. Re-design the logic to either assert outside the transaction block or restructure the publishing mechanism.

## 4. Resetting the Environment
If your local development database gets corrupted:
```bash
docker-compose -f docker-compose.dev.yml down -v
docker-compose -f docker-compose.dev.yml up -d
npx nx serve api
```
This drops the volume and restarts Postgres with a clean slate.
